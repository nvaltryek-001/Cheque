# Deployment verification

Date: 2026-11-01 · branch `chequeverify-v2` · target: Render (Docker web service with a persistent disk).

**Nothing has been deployed to Render and no Render service exists, so there is no public address yet.** Everything below was
verified on a development machine or in a real Docker container on GitHub Actions. What only a real Render deployment can show is
listed in section 6. Nothing here contains a secret, a password or private data.

`23df57e` carries the final code (the demo-sample feature included); the commits after the last code change (`ba79a2a`) change documentation only. All 13 steps passed on its push run and on its pull-request run, and so did the other four jobs (`backend`, `frontend`, `dependency-audit`, `private-data-audit`).

What the failures were (all found by these checks, none by chance):
* **Proxy step on `335baf8`: a real application bug.** Waitress 3 removes `X-Forwarded-*` headers before the application sees them, so
  behind Render every visitor would have shared one address (one sign-in throttle for everyone, wrong addresses in the audit log) and
  HSTS would not have been sent. Fixed with `clear_untrusted_proxy_headers=False` (`CV_PROXY_HOPS` stays the only trust setting) and
  pinned by a test that fails without it.
* **A related bug found while repeating the stop tests:** the SIGTERM handler could fail to start its watchdog (a signal arriving during a
  `print` raised "reentrant call"), so a stuck request could keep the process alive until the platform killed it. Fixed; the new test fails on the
  old code; 60 of 60 repeated stop runs under CPU load ended in about 1 s.
* **Read-only step on `335baf8` and `93c2f0c`: a mistake in the test script, not in the application.** The probe ran inside the container but
  asked for the host-side port (8003); the server listens on 8000 there. After the fix the step passed on GitHub, and the same workflow
  also passed 32 of 32 in a local rehearsal with the application tree mounted read-only and the server running as an unprivileged user.
* Two earlier failures were mistakes in the CI script itself (`docker top` without the `pid` column; a missing `if: !cancelled()` so one failure hid
  the rest) and are fixed.

## 4. Speed (what "fast result" means in numbers)

On a 2-CPU development machine each cheque needs about **4.2 s** of OCR (median; slowest 4.8 s; the first request after start 4.0 s because it loads the models).
Eight uploads at the same moment all succeed and finish after 18.5 s because two are processed at a time. The time is OCR work, not upload time. A Render
Starter instance has less CPU than the machine used for these figures, so expect longer there; a larger plan (more CPU, then raise `CV_MAX_CONCURRENT_IMAGES`)
is the direct way to get results sooner. Details: `DATASET_TEST_RESULTS.md`.

## 5. Dataset on the hosted copy

The private datasets are not in git or in the image, so the hosted application starts empty. After signing in as administrator, load cheques with
*Batch upload* (up to 20 per batch) or the upload box on *Cheque verification*. The *OCR dataset* page and its *Process with OCR* button work wherever the dataset folder
exists (the development machine, or a server given `CV_OCR_DATASET`).

## 6. Not verified, and needs a real Render deployment

* That Render's own build of this Dockerfile succeeds and starts (the same Dockerfile builds and runs on GitHub).
* How Render mounts the disk (ownership and permissions): CI imitates it with a root-owned folder; the entrypoint handles that case, but Render's disk is untested.
* That Render sends exactly one trusted proxy hop in `X-Forwarded-For` / `-Proto` as `CV_PROXY_HOPS=1` assumes: CI imitates the proxy.
* Behaviour at a Render deploy and stop: Render sends SIGTERM and waits 30 s; the server's own limit is 20 s (`CV_STOP_GRACE_SECONDS`). A service with a disk is not
  replaced without a short outage.
* Speed and memory on the Starter plan (CPU share, 512 MB): GitHub's 512 MB container check passed, but Render's instance is a different machine.
* Real e-mail delivery: no mail server was available; the SMTP path was tested only against a local fake server. Until `CV_SMTP_*` are set, only the administrator
  sign-in works.
* TLS, a custom domain, Render's log retention and its health-check timing.
* Start-up refusal on a weak first password: if `CV_ADMIN_PASSWORD` is shorter than 12 characters, all letters or all digits, or a common word, the service stops with
  "CV_ADMIN_PASSWORD is not acceptable" in the Render log (by design; tested locally).
